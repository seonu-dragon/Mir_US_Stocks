# 거래 원장 설계 (2026-10-23)

배경: `2026-10-23_레퍼런스조사/0_종합.md` §5, 부록 `7_포트폴리오·배당도구.md` #1·#2·#4·#12.
지금 보유는 종목마다 '수량 + 평단' 스냅샷 하나뿐이다. 그래서 실현손익, 기간 수익률(TWR/XIRR), 받은 배당 기록처럼
거래 이력이 있어야 계산되는 기능이 모두 빠져 있다. 이 문서는 원장의 데이터 모델과 기존 보유와의 관계를 정하고,
1단계(매수·매도 입력과 실현손익)를 구현한 내용을 적는다.

원칙(기존과 같음): 데이터는 브라우저에만 저장한다. 사용자가 넣지 않은 값(수수료·세금·환율)은 지어내지 않는다.
모르는 값은 '모름'으로 둔다.

## 1. 데이터 모델

거래 한 건(`ledger-core.js normalizeTx`):

| 필드 | 형식 | 설명 |
|---|---|---|
| `id` | 문자열 | `tx_<시각36진><순번><난수>`. 백업 병합의 키 |
| `market` | `us` \| `kr` | 저장 키와 같은 시장 |
| `ticker` | 문자열 | 보유와 같은 티커 표기(US 대문자, KR 6자리) |
| `type` | `open` \| `buy` \| `sell` \| `split` \| `dividend` \| `fee` | `open` = 시작 잔고(아래 §2) |
| `date` | `YYYY-MM-DD` | 체결일. `open` 만 `""`(모름)을 허용한다 |
| `qty` | 수 | 주식 수(소수 허용 — 미국 소수점 거래) |
| `price` | 수 | 체결가(거래 통화). 배당·수수료는 금액 |
| `ratio` | 수 | `split` 만. 1주당 새 주식 수(4:1 분할 = 4, 1:10 병합 = 0.1) |
| `currency` | `USD` \| `KRW` | 시장에서 정한다 |
| `fee`, `tax` | 수(0 이상) | 사용자가 넣은 값만. UI 는 '수수료·세금' 한 칸으로 받아 `fee` 에 넣는다 |
| `fx` | 수(선택) | 미국 거래의 원/달러 환율. 사용자가 넣었을 때만 있다 |
| `note` | 문자열(≤200) | 메모. 시작 잔고는 '원장 시작 전 보유' |
| `createdAt` | ms | 입력 시각(정렬에는 쓰지 않는다) |

저장: `localStorage` 시장별 키 `mir_ledger_v1:us` / `mir_ledger_v1:kr`, 값 `{ v: 1, txs: [...] }`. 읽기·쓰기는 전부
`window.safeStorage`(try/catch)를 거친다. 거래가 0건이 되면 키를 지운다.

적용 순서: 날짜 오름차순, 같은 날은 입력 순서. 날짜를 모르는 시작 잔고는 맨 앞이다.

## 2. 기존 보유와의 관계 · 이전(migration)

- **원장에 거래가 하나라도 있는 종목**: 보유의 수량·평단을 원장에서 계산한 값으로 덮는다(`reconcileHoldings`).
  전량 매도한 종목은 보유에서 빠지고, 원장에만 있는 종목은 보유에 추가된다.
- **원장에 거래가 없는 종목**: 지금과 똑같이 동작한다. 원장이 비어 있는 사용자는 아무것도 바뀌지 않는다(테스트로 고정).
- 보유 목록(`mir_portfolio_v1:<시장>`)의 형식 `{ticker, qty, avgCost}` 는 그대로다. 그래서 보유를 읽는 모든 화면
  (배당·리밸런싱·리스크·룩스루·대시보드 위젯·클라우드 동기화)이 고칠 것 없이 원장 결과를 본다.
- 덮는 시점: `loadPortfolio`(부팅·시장 전환), `savePortfolio`(모든 보유 변경), `applyCloudPortfolio`(클라우드 pull).
  원장이 우선이므로, 원장 종목은 CSV 가져오기·클라우드 값보다 원장 값이 이긴다.
- **이전**: 어떤 종목에 처음 거래를 넣을 때 그 종목에 보유가 있으면, 그 수량·평단을 `open`(시작 잔고) 거래로 먼저
  넣는다. 보유에는 만든 날짜가 없으므로 날짜는 `""`(모름)이고, 사용자가 나중에 편집해서 날짜를 넣을 수 있다.
  사용자가 아무 거래도 넣지 않으면 이전도 일어나지 않는다(일괄 이전하지 않는다).
- 보유 표에서 원장 종목은 부제에 '· 기록'이 붙고, 편집 칸 대신 '거래 기록으로 계산됩니다' 안내가 나온다.
  수동 '+ 종목 추가'로 원장 종목을 덮으려 하면 거부한다.
- 삭제: 보유 행 '종목·거래 기록 삭제'(두 번 눌러야 함)와 '전체 삭제'는 해당 종목/시장의 거래도 같이 지운다.
  남겨 두면 원장 종목이 보유로 다시 계산돼 돌아오기 때문이다. 거래 하나를 지워 그 종목 거래가 0건이 되면,
  지운 것이 시작 잔고였으면 보유는 그 값으로 남고(이전 되돌리기), 매수였으면 보유에서도 뺀다.

## 3. 원가 계산: 이동평균

국내 증권사 앱의 '평균단가'는 이동평균이다. 매수할 때만 평단이 바뀌고, 매도는 평단을 바꾸지 않는다.
미국 세법의 기본값은 FIFO(종목별 지정 가능)지만, 1단계는 국내 사용자 관행과 기존 보유의 '평단' 의미에 맞춰
이동평균 하나만 쓴다. FIFO·특정 로트 지정은 3단계 이후 선택지로 남긴다(원장 이벤트가 그대로 있으니 계산만 추가하면 된다).

- 매수: `평단 = (보유수량×평단 + 수량×체결가) / (보유수량+수량)`.
- **평단은 수수료를 넣지 않은 체결가 평균**이다(증권사 앱의 평균단가와 같은 값 → 보유 표와 맞는다).
  매수 수수료·세금은 종목별 `feePool` 에 쌓고, 매도할 때 매도 수량 비율만큼 꺼내 실현손익에서 뺀다.
  수수료 포함 평단이 필요하면 `avgCostInclFees` 를 쓴다.
- 매도 실현손익 = `매도금액 − 평단×수량 − 배분된 매수 수수료 − 매도 수수료·세금`(순손익).
  수익률 = 실현손익 ÷ (평단×수량 + 배분된 매수 수수료).
- 전량 매도: 수량·평단·`feePool` 이 0 이 된다. 다음 매수는 새 평단에서 시작한다.
- 과매도: 그 시점 보유보다 많이 파는 매도는 적용하지 않고 오류로 남긴다. UI 는 그런 추가·수정·삭제(앞의 매수를
  지워 뒤의 매도가 과매도가 되는 경우 포함)·백업 병합을 거부한다(`tryChange`, `mergeImport`).
- 분할: 보유수량×ratio, 평단÷ratio. 원가 총액은 그대로다. 단주 현금 정산은 다루지 않는다(사용자가 매도로 넣는다).
  상세 데이터의 `splits` 로 제안한다(2단계, §8.3 — 사용자가 확인해야 기록).
- 배당(`dividend`)·단독 수수료(`fee`)는 코어가 이미 받는다. 배당은 포지션에 영향이 없고 `dividends` 목록에 쌓인다.
  단독 수수료는 실현손익에서 뺀다. 배당 입력 칸은 2단계에서 열었다(§8.2). 단독 수수료 입력 칸은 아직 없다.

## 4. 환율(미국 종목)

- 미국 거래는 달러로 계산한다. 화면의 실현손익도 달러다.
- 거래에 환율(`fx`, 원/달러)을 넣었을 때만 원화 실현손익을 낸다. 조건: 그 포지션의 모든 매수(시작 잔고 포함)에
  환율이 있고 매도에도 환율이 있을 것. 원화 원가도 이동평균으로 따라간다(매수 금액+수수료를 그날 환율로 환산).
  하나라도 빠지면 그 매도의 `pnlKrw` 는 `null` 이고, 원화 합계에서 빠진다. 오늘 환율이나 과거 환율 데이터로 채우지 않는다.
- 요약 칸은 원화 값이 있는 매도가 있을 때만 '원화 +…'를 덧붙인다.

## 5. 동기화

- 1단계는 **로컬 전용**이다. 워커와 동기화 형식은 바꾸지 않았다. 보유 목록은 지금처럼 동기화되므로 다른 기기에서는
  원장 결과로 계산된 수량·평단까지만 보인다(원장 자체는 안 간다).
- 백업: '⋯ › 백업 내보내기(JSON)'·'백업 가져오기'. 형식 `{app:"mir-ledger", v:1, market, exportedAt, txs}`.
  가져오기는 id 기준 병합(같은 id 는 교체)이고, 합친 결과에 과매도가 생기면 전부 거부한다. 다른 시장 백업은 거부한다.
- **클라우드 동기화 제안(구현하지 않음)**: 워커 `/sync/prefs` 는 필드를 화이트리스트로 거르고 본문을 32KB 로 자른다.
  거래 한 건은 JSON 으로 약 150~180바이트라, 지금 prefs 가 쓰는 몫을 빼면 남는 자리로는 100건 남짓밖에 못 싣는다.
  제안:
  1. 별도 엔드포인트 `/sync/ledger`(같은 인증·같은 KV 네임스페이스, 키 `ledger:<user>:<market>`), 본문 한도 256KB.
  2. 싣는 형식은 짧은 키 배열 `[id, type, ticker, date, qty, price, fee+tax, fx?]`(약 70바이트/건 → 256KB 에 3천 건).
  3. 병합은 id 기준 합집합 + 삭제 묘비(`deleted: [id…]`, 90일 보관). 마지막 쓰기 우선은 거래 단위로만.
  4. 워커 화이트리스트에 `ledger` 를 추가하고, 프론트는 `scheduleCloudSyncPush` 와 같은 디바운스로 따로 보낸다.
  워커는 수동 배포라 머지와 배포 순서를 맞춰야 한다(옛 워커면 404 → 조용히 로컬 전용 유지).

### 8.1 기간 수익률(TWR·XIRR)

- **가격**: 상세 `chartSeries` 종가는 분할이 소급된 수정 종가다(미국 야후, 국내 네이버 수정주가 — NVDA 2024-06-07 봉이 120 대).
  원장 수량은 분할 전 날짜엔 분할 전 주식 수이므로 실제 종가로 되돌린다:
  `실제 종가(d) = 수정 종가(d) × Π(d 이후 분할 비율)`. 분할 목록 = 상세 `splits`([날짜, 분자, 분모]) ∪ 상세에 없는
  원장 분할 거래(±7일 안에 상세 분할이 없을 때). 상세에 분할이 있는데 원장에 기록이 없으면 그 종목(과 포트폴리오)은
  수익률을 '—'(분할 미기록)로 두고 분할 제안을 먼저 띄운다.
- **TWR**: 날짜 축 = 원장 종목 봉 날짜의 합집합. 거래는 그 날짜 이후 첫 봉에 배정, 마지막 봉 뒤 거래는 기간 밖.
  거래(현금흐름)가 있는 날은 **체결 시점에서 구간을 나눈다**:
  `Vpre = Σ 직전 수량 × (그날 거래한 종목은 체결가, 아닌 종목은 그날 종가)`,
  `r_a = Vpre / V(전날)`, `r_b = (V(그날 종가) + 유출) / (Vpre + 유입)`, 하루 수익 = `r_a × r_b`.
  유입 = 매수금액 + 수수료·세금, 유출 = 매도금액 − 수수료·세금 + 배당(세후) − 단독 수수료. 거래 없는 날은 `V/V(전날)`.
  기간 TWR = Π(하루 수익) − 1(누적, 연환산 아님). 분할은 그날 시가부터 새 주식 수(현금흐름 아님).
- **기간**: 1M = 기준일 −30일, 3M = −91일, 1Y = −365일, YTD = 전년 12-31, 전체 = 첫 거래일부터. 기준일 = 마지막 봉
  (포트폴리오는 지금 보유 중인 종목들의 마지막 봉 중 가장 이른 날). 기간 시작 종가가 기준값.
- **'—' 규칙(메우지 않음)**: 기간 시작이 첫 거래보다 앞(보유 기간 짧음) · 기간 시작이 봉 시작 전 · 보유 중인데 그날
  종가가 없음(다른 종목만 거래한 날은 7일 이내 직전 종가를 그대로 씀 — 마지막 체결가, 보간 아님) · 연속 봉 간격 10일 초과 ·
  상세 파일 없음 · 날짜 모르는 시작 잔고(전체·XIRR) · 기간 중 보유 없음. 칸 title 에 사유.
- **XIRR**: `dca-core.js` `xirr` 재사용(연 365일). 흐름 = 날짜 있는 모든 거래(매수 −, 매도·배당 +, 단독 수수료 −) + 기준일
  평가액(+). 중간 봉은 필요 없다(첫 거래가 봉 시작 전이어도 계산). 날짜 모르는 시작 잔고가 있거나 기간이 30일 미만이면 '—'
  (짧은 기간 연환산 과장 방지). 전체 기간만 낸다.
- 알려진 한계: 국내 ETF 는 네이버 수정주가에 분배금까지 소급돼 있어, 분배금을 배당으로 기록하면 TWR 에 이중으로 들어간다.
  일봉이 상세 파일 대신 워커 실시간 대체(`__liveGenerated`)면 배당·분할 이벤트가 없어 제안·분할 검사를 하지 않는다.
- 화면: 거래 기록 카드 요약 아래 '기간 수익률' 표(포트폴리오 — 원장 종목 2개 이상일 때 — + 종목별) × 1M·3M·YTD·1Y·전체·XIRR.

### 8.2 배당 수령 기록

- 구분 '배당': 입금일 · 금액(세전, `price`) · 원천징수(`tax`) · 환율(선택). 확인한 제안에서 들어오면 `exDate` 를 함께 저장한다.
- **제안('받았을 배당(추정)')**: 상세 `dividends`([배당락일, 주당]) 중 원장 첫 날짜 거래 뒤·오늘까지의 배당락마다
  `배당락 전날까지의 원장 수량 × 주당 × Π(배당락 이후 분할 비율)`(상세 배당도 분할 소급이라 그때 주식 수 기준으로 되돌림).
  제외: 같은 `exDate` 로 기록된 배당, `exDate` 없이 배당락 ~ +60일 안에 기록된 배당, '무시'한 것(`mir_ledger_dismiss_v1:<시장>`),
  기록 안 된 분할 뒤의 배당락(원장 수량이 분할 전이라 틀림 — 분할 제안이 먼저), 그 시점 보유 0.
  '추정' 배지를 달고, '확인·기록'을 눌러도 바로 저장하지 않는다 — 금액·날짜가 채워진 폼이 열리고 사용자가 실제 입금일·금액·
  원천징수로 고친 뒤 '기록'을 눌러야 원장에 들어간다.
- 요약: '올해 받은 배당'(세후, 부제에 세전·원천징수·건수·누적).
- **금융소득 2천만 원 계기판**(portfolio.js): 그 시장 원장에 올해 배당 기록이 있는 종목은 '지급' 몫을 기록 세전 합계로 바꾸고
  남은 달만 기존 추정(예정)으로 둔다. 기록 없는 종목·시장은 예전 추정 그대로. 범례 '지급(기록)' 또는 '지급 기록 X + 추정 Y',
  기준 문구 '받은 배당은 기록 기준(N건)'. 비과세 계좌 표시 종목의 기록은 뺀다. 다른 시장 저장값에 `recorded` 가 함께 남는다.

### 8.3 분할 제안

- 상세 `splits` 중 원장 첫 날짜 거래 뒤(초과)·오늘까지, 직전 보유가 있고 ±7일 안에 기록한 분할이 없는 것. 병합(1:10 → 0.1)도.
  '확인·기록' → 날짜·비율이 채워진 분할 폼 → 사용자가 '기록'. 제안 목록은 분할을 먼저 보여 준다.

- 배당 제안: 배당락 전날 수량(부분 매도 반영), 기록·무시·미래 제외, 분할 소급 되돌림, 미기록 분할 뒤 제외. 분할 제안: 병합 포함.
